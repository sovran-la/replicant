## Verdict: do not merge until A1 is fixed

A **marker resumes every unit it covers, not only its own.** If a pull of
the loose unit `work` is interrupted (rsync exit 23 or 24, a timeout, a lost
lease), the leaf's marker `work` covers every repo under `work`, and the next
`sync` decides **all of them** `resume pull`, whatever their baselines say.
Reproduced three ways: a commit made only on the leaf is pulled over; an edit
made only to a leaf loose file is pulled over; a brand-new repo that exists
only on the leaf is **deleted outright** (34 files, no refusal, no
confirmation, `sync --yes` exit 0). The reverse holds too: a marker on a repo
makes its loose unit `resume pull`. This is the catastrophic outcome. It needs
an interrupted pull first, so it cannot happen on the first sync (a push),
but it is one exit-24 away on every pull after that. The fix is small: resume
only on a marker for exactly this unit (below; with it the whole suite and
the three reproductions pass). A2 and A3 are also pulls over leaf work, by
design rather than by accident. Decide on them before the first rollback or
the first interrupted pull on birchbook, not necessarily before merge.

Everything else that touches the sender holds up. A push never writes the
leaf's tree: source and destination order, the empty stand-in, `--delete`, and
the list operations all aim at home. The leaf writes only hashed records under
its state dir. Rollback runs on home only. `--yes` cannot confirm a deletion.
A dry run cannot write.

## Findings

### Blocker

**A1. A marker over a neighbouring unit forces `resume` on it, skipping the
direction table.** `src/plan/decide_all.rs:35-36` passes
`marker::covering(..)`, which matches ancestors and descendants
(`src/marker.rs:62-64`). `src/decide.rs:181-197` then returns
`Resume { direction: m.direction }` for any covering marker. The
vanished-source check applies only when `m.rel == i.rel`, so a covering
marker whose unit is empty on the source side turns into a whole-unit delete:
the transfer gets `source_absent` (`src/plan/diff.rs:137`). The test
`src/decide_resume_tests.rs:156` asserts exactly this case: a loose leaf
unit, home `Empty`, resume pull.

Reproduced (each after a clean first sync, with a fake rsync that fails the
real run of one unit with exit 23):

| marker left on the leaf | then, on the leaf only | next `sync --yes` |
|---|---|---|
| `work` (loose pull interrupted) | commit `mine.txt` in `work/alpha` | `work/alpha` = `resume pull`; commit and file gone, `git log` back to `init` |
| `work/alpha` (repo pull interrupted) | edit `work/notes.txt` | loose `work` = `resume pull`; edit reverted |
| `work` (loose pull interrupted) | new repo `work/fresh`, committed, clean | `resume pull` from an empty source; **34 deletions, repo gone**, no refusal, outcome `Done` |

Guardrail 1 does not help. It sees uncommitted work only, and loose units
have no equivalent.

Fix: a marker resumes only its own unit. Other hosts' markers keep the
covering quarantine.

```rust
// src/plan/decide_all.rs
leaf_marker: leaf_markers.iter().find(|m| m.rel == l.rel),
home_marker: snap.markers.iter()
    .find(|m| m.covers(&l.rel) && m.host != ctx.me)
    .or_else(|| snap.markers.iter().find(|m| m.rel == l.rel)),
```

With exactly this change the suite passes: 465 tests plus the three
reproductions, 468 in total. Also invert `decide_resume_tests.rs:156`, or
better, make `decide` itself ignore a non-exact own marker so the rule lives
in one place, and keep the three reproductions as regression tests. The
loose transfer already excludes the repos inside it, so neither unit's
resume needs the other's marker.

### Should fix

**A2. Rolling back a finished push makes the pusher's next sync pull home's
old state over the leaf.** This is by design (`src/daemon/home_rollback.rs:9-10`,
the notes' "Rollback" section) but untested. Reproduced with the
`pushed()` fixture from `home_rollback_tests.rs`: after both pushes are
rolled back, the leaf plans `work` = `pull` and `work/alpha` = `pull`, with 0
refusals. `sync --yes` reverts the leaf's loose edit, deletes its new tree,
and resets the leaf-only commit in `alpha`. The leaf's versions survive only
in home's `backup/<push>/rollback/`, which the sweep deletes with the push
after `backup_days` (default 14). The first real sync is a push from
birchbook, and rollback is the advertised safety net for it. So the likely
sequence is "push went wrong → roll back on home → `sync` on birchbook", and
that sequence overwrites birchbook's tree. Fix: home reports rolled-back
pushes per unit in `HomeSnapshot` (the manifest has host, unit and
`rolled_back_at`). The pushing host decides those units as a blocking
conflict ("home rolled back your push `<id>`") until it is explicitly
accepted, the same pattern as `--confirm-delete`.

**A3. A resumed pull deletes or overwrites leaf work made after the
interruption.** PLAN says a dead pull resumes, "never a conflict", and a
marker records only the source's state. Reproduced: interrupted pull of loose
`work`, then `work/todo-made-later.md` created on the leaf. The dry run shows
`- todo-made-later.md` and `sync --yes` deletes it. The same holds for a
resumed confirmed deletion or removal (`resume` with an `Empty` source state,
`decide_resume_tests.rs` "still a resume"): its confirmation is reused for
whatever the leaf has created there since. Interactive users see the `-`
lines; `--yes` does not stop. Fix: in the resume path, refuse (like
guardrail 1, overridable by an explicit per-unit confirmation) any target
path the dry run deletes or replaces whose mtime is after the marker's
`started_at`.

**A4. The write-set gate cannot see a new rsync write, or a write through an
alias.** `src/write_set_tests.rs:17-41` matches text. It counts the one
`Command::new(` in `rsync/child.rs`, but no rsync entry point: `child::run(`,
`.apply(`, `copy_listed(` and `delete_listed(` are not patterns. Reproduced:
the gate stays green with `let _ = transfer.apply(&runner);` added before the
dry run in `src/plan/diff.rs` (a real transfer during `--dry-run`), and with
`use std::fs::write as save_bytes; save_bytes(p, ..)` added in
`plan/apply.rs`. The first mutant is caught elsewhere: 48 behavioural tests
fail. Nothing catches the second. The notes call this gate the write set
"held to the code", and for synced paths it is not. Fix: add the four rsync
entry points with their current counts (`rsync.rs` 1, `rsync/apply.rs` 3 +
1 + 1, `plan/apply_unit.rs` 1, `home_backup.rs` 1, `home_rollback.rs` 3).
Forbid `use std::fs::{`/`use std::fs::<fn>` imports and `Command as` aliases
outright. Add the writing `libc::` calls (`unlink(`, `rename(`, `open(`,
`mkdir(`, `symlink(`, `chmod(`).

### Note

**N1. Ctrl-C during apply does not stop the apply.** The CLI only waits on
the leaf daemon (`src/daemon/local.rs:34-46` runs the request to completion,
and nothing watches the CLI's socket). After Ctrl-C mid-apply, disk ends up
exactly as if the CLI had kept waiting. That is safe, but the failure table
has no row for it, and the only way to stop a pull in progress is to kill the
daemon, which leaves a marker. With A3 unfixed, that marker is a hazard.
Document it, or have the daemon raise the plan's `Abort` when the CLI hangs
up.

**N2. Rollback's delete list comes from what the leaf reported, unchecked.**
`Settle`/`Interrupted` `changes` are stored verbatim
(`src/daemon/home_backup.rs:238`), and `undo()` turns every `+ path` into a
`delete_listed` entry under the unit. The `backed_up` list is `check_rel`'d
(`home_backup.rs:149`) but this one is not. This is home only, and the leaf
is trusted to its rsync over ssh anyway, but one `check_rel` in `record_run`
closes it.

**N3. Test isolation depends on convention.** `LeafConfig::home_dir()` falls
back to the real `$HOME` when unset (`src/config/leaf.rs:105`). No current
test does that (every apply test goes through `Bed` or `test_certs::pair`,
both set `home_dir`), but nothing would stop one. Make `user_home()` panic
under `cfg(test)`.

**N4. First push of a live tree.** `Ran::ok` treats exit 24 (vanished) as
interrupted, correctly. But a push of a tree an editor is writing to (swap
files, `.DS_Store` churn) can end in 24 every time, which leaves home
quarantined until it doesn't. It is not damage. Expect it on birchbook's first
push, and keep such files in the root's excludes.

## Verified OK (what I checked, and how)

1. **Nothing writes the sender during a push.** Push argument order is
   `[leaf, home]` (`src/rsync.rs:216-219`); `--delete` acts only on the
   destination; the empty stand-in replaces only the *source* endpoint
   (`rsync.rs:173-176`); a single-file deletion targets `home_path` for a push
   (`rsync/apply.rs:107-110`). On the push branch the leaf runs only a dry
   run, `BeginPush`, the transfer, `Rehash`/`Agree`/`Settle`, and its
   baseline (`plan/apply_unit.rs:157-275`). Leaf markers are written for
   pulls only. Records live under `state/` with SHA-256 file names
   (`record.rs:31-35`), so no `rel` can escape. Rollback is home-only: the leaf
   daemon refuses it (`daemon/leaf.rs`), and it is reachable only from
   home's local socket. `--as` mapping (`config/leaf.rs:138-151`,
   `check_local`) and home's `spec_of`/`check_rel` on every apply request
   keep writes inside a served unit. Existing tests fingerprint both trees
   around push and pull (`apply_tests.rs` "writes exactly what rsync
   itemized", source untouched).
2. **Direction.** Walked every row of `decide.rs` and `decide/unserved.rs`:
   no-baseline (empty→pull/push, identical→nothing/adopt,
   different→conflict), unchanged, one side changed, both changed,
   `DeletedOn` either side (carved out before pull/push; `direction() ==
   None`), `Remove` (unsubscribed and unchanged and unmarked only),
   own-removal resume, and a resume whose source vanished (conflict for an
   exact marker). The only inputs that pull over leaf-only work are the
   marker rows (A1, A3) and a rolled-back push (A2).
3. **Write set.** Every allowed count matches the code, and each reason is
   accurate (e.g. `apply_unit.rs` `.put(` 2 = marker + baseline; `home_apply.rs`
   2/2; `home_backup.rs` put 2/delete 1). There are no `libc` writes outside
   scratch `mkstemp`/`mkdtemp`, and no `use std::fs::` item imports or
   `Command` aliases today. The gate's blind spots are A4.
4. **Failure matrix.** Read each path against the notes' table; it holds.
   rsync nonzero or 24 means no baselines and the marker kept

   KILL after 2 s (`rsync/child.rs:112-131`); the leaf declares a lease lost

   have expired it. Ctrl-C at the prompt sends nothing; Ctrl-C mid-apply is

5. **`--yes` never confirms `DeletedOn`.** `gate()` (`plan/apply.rs:153-185`)
   passes a `DeletedOn` only if a `confirm_delete` entry `confirms` it:

6. **Backup and rollback.** The backup list is every non-directory change

## What's done well

- The empty stand-in is built with `mkdtemp`, and so are the delete skeleton
  and the list files, so a planted `/tmp` path cannot become the source of a
  `--delete`.
- Deleting by exact list (`delete_listed`), with its skeleton refusing to
  follow or replace symlinked ancestors, is careful work, and the tests probe
  exactly the cases that would bite.
- Taking the backup by hand instead of trusting `--backup` was the right
  call, and the probe that found openrsync dropping `--delete` is the kind of
  thing that never gets caught until it costs data.
- Home's writes are gated on holding the head of the queue with a *sync*
  entry, which makes a dry run's lease structurally harmless.
- The failure table in the notes is accurate. That is rarer than it should
  be.
