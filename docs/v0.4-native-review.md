# v0.4-native review

Reviewed 2026-11-03. Branch `bsneed/v0.4-native`, `5e5f8cb200dc6303f19df00e58513b8145f46933`
against `main` `15455e1a138701d39844d4de01a91be7db453cd3` (`15455e1..5e5f8cb`, ten
commits). Clean tree, no uncommitted input.

## Verdict: not yet

The transport's core is sound: whole files, ordering, stall handling and the
write set all held under attack. Three things block the merge. All three are
reproduced in an isolated `git archive` copy with its own `CARGO_TARGET_DIR`.

| | What | Fix size |
|---|---|---|
| **B1** | A pull deletes or overwrites leaf-only work made after the plan was confirmed. Not a regression (also reproduced on `main`), but it is the catastrophic outcome, and the fix is now the push's own five lines. | small |
| **B2** | A socket in a unit fails that unit on every sync and stops every later unit. A FIFO hangs the sync forever, and Ctrl-C cannot stop it. A real socket sits in `~/work` on birchbook. | small |
| **B3** | A frame over 8 MiB hits an `assert!`: the transfer panics, usually wedges forever, and holds home's queue. Triggers: a small file growing past 8 MiB mid-transfer, or a push deleting about 80k paths. | small |

Fix before the first real push, but they need not hold the merge: M1 (rollback
is not a round trip), M2 (receiver containment against a bad peer), M3 (an
interrupted repo pull can block its own resume), M4 (core invariants have no
behavioural test).

No finding has an honest peer writing outside a unit, tearing a file, or a push
writing the sender. M2 needs a compromised or buggy authenticated peer.

## Blockers

### B1. A pull re-diffs after the plan was confirmed and never compares (class 1)
`src/plan/apply_unit.rs:141`, `src/plan/xfer.rs:104-110`. Compare the push at `apply_unit.rs:111-113`.

A pull passes `fresh = None`, so `Ops::apply` takes a new dry run and carries it
out. Nothing compares it to the plan the human confirmed. A push does compare,
and stops with "it changed since the plan was made".

**Reproduced** (`g1`): clean first sync, one edit on home, then a hook fires as
the unit's transfer starts. It creates a new leaf file and a new leaf repo, and
edits a leaf file. Result: `Outcome::Done`, journal `sync pull 2 files 28 del
0.0s ok`. The new file is gone, the new repo (with `.git`) is gone, and the leaf's
edit is overwritten. There was no prompt and no backup, because a leaf has none.
The same probe through the real `rsync` wrapper on `main`: `Outcome::Done`, file
deleted. So this is **pre-existing**, with the window now moved to the native
code.

The window runs from `--yes` or the prompt to that unit's start. On a 155-unit
sync that can be many minutes, and agents write to the tree during it. Git-ignored
paths are in the window too: the exclude list was built at plan time, so a build
artefact created after it is not excluded and is deleted (inspection). Confirmed
deletions and removals use the same path.

**Fix:** in the `Direction::Pull` arm, take `ops.dry_run(t)`, compare it to
`u.diff` as the push does, stop before the marker on a mismatch, and pass it as
`fresh`. A short window remains between that dry run and each write. Narrowing it
further (re-`lstat` against the target manifest before a delete or overwrite) is
worth doing but need not hold the merge.

### B2. Every non-regular file is listed as a regular file
`src/native/manifest.rs:73-77`, `src/native/source.rs:104-111`, `src/native/send.rs:94-99`.

`Entry::of` falls through to `EntryKind::File` for sockets, FIFOs and devices, so
the diff asks to send them.

- **Socket, reproduced** (`p04`, three runs): `open` fails, so it is "changed, not
  sent", and verification fails every time with `after the transfer 1 paths still
  differ from the source (changed while it was sent?): socket`. The marker stays,
  the resume does the same, and `apply_all` stops at the first unit that does not
  finish, so **no later unit ever runs**. The message points the wrong way.
- **FIFO, reproduced** (`p05`): `source::open` blocks in `open(2)` with no writer.
  The abort was raised at 3 s and nothing returned; the process was killed by a
  25 s alarm (exit 142). The monitor can shut sockets but cannot wake `open`, so
  the thread scope never ends. By inspection, `with_heartbeat` keeps renewing the
  lease meanwhile, so **home's queue is held until the daemon is killed**. On a
  pull the same open pins a home thread and its stream slot (inspection).

**This is on the owner's machine:** `~/work/scratch/firstlook-live/home/socket`
(dated Oct 22, not in a repo, so loose `work` unless a root exclude covers it; I
did not read thistledown's fleet.toml). `~/.sovran/agents/socket` also exists, if
that path is subscribed. A repo with `core.fsmonitor` keeps a socket in `.git/`
(not seen here). v0.3 passed `rsync -a`, which handles specials.

**Fix:** a third outcome in the walk: not file, link or directory means not listed
and never opened, on both sides. Keep `repos::entry` and the state walk consistent
with it. Open with `O_NONBLOCK` and check `is_file()` on the fd as a second line of
defence. Add it to Known limits, and consider counting skipped files in the unit's
notes.

### B3. `assert!` on frame size; a panic can wedge the transfer
`src/native/frame.rs:170`, `src/native/send.rs:126-143`, `src/native/source.rs:93-94`,
`src/native/transfer_run.rs:180,192,195,208,212` (frame), `:113,:219` (wedge).

"Frames are built small" is false in two ways:

1. A batch's sizes are the sizes **at read time**. A file under 64 KiB at the diff
   and over 8 MiB when sent is read whole with no cap and goes into one frame.
2. `Clean`, `Replace`, `Mkdirs`, `Deletes` and `DirModes` each put their entire list
   in one frame.

The monitor stops only when `watch.over` is set at `:219`. A panic unwinds past
that line, so the outer scope waits for the monitor forever.

| Probe | Trigger | Result |
|---|---|---|
| `p01` | small file grown to 9 MiB after the dry run | panic in worker, then **hang** (alarm, exit 142) |
| `p03` | 90k directories in `Mkdirs` (fabricated list) | panic, then **hang** (alarm, exit 142) |
| `p02` | real push deleting 80k files, ~100-byte paths | panic out of the leaf's sync thread, on every retry |

The owner's loose `work` is 70,713 files, so deleting a large part of it is in
range (about 8 MiB / (path + 12) bytes). Home's own pull path hits the same assert,
but only its connection thread dies (inspection).

**Fix:** return an error instead of asserting. Send a batch entry that has grown
past `SMALL` as a big file, or call it `Changed`. Split the list frames, or stream
them one entry at a time. Set `over` from a drop guard so no panic can wedge the
monitor. Test each with the probes above.

## Major

### M1. Rollback is not a round trip
`src/daemon/home_rollback.rs:65,71`, `src/native/backup.rs:53`, `src/native/local.rs:46-55`.

The notes claim "restoring home exactly (bytes, modes, mtimes to the ns, links,
dirs)". The test tree has no kind changes, deleted empty directories, or private
directories. All reproduced:

| Probe | Push did | `rollback` |
|---|---|---|
| `p10` | dir `a/b` → file `a` | **Err**: `a is not a directory`. `seen` drops `+ a` because `- a/` used the same path, so the new file blocks the restore. |
| `p11` | file `a` → dir `a/b` | **Err**: `"a" is a directory, not a file`, while keeping the pushed copies. Nothing restored. |
| `p12` | deleted `priv/` (0700) with a file | Ok, but **`priv` comes back 0755**: a private directory is widened. |
| `p13` | deleted an empty dir | Ok, directory not restored. |
| `p14` | dir mode 0700 → 0755 | Ok, mode not restored. |

In `p10` and `p11` the originals are safe in `backup/`; the operator restores by
hand. `undo()`'s logic is unchanged from `main`, and I did not test these on `main`.

**Fix:** record each directory's mode and existence in the run's manifest when it
is removed or changed; `create_dir_all` in `keep` loses it. Make `undo` handle two
lines on one path, deleting the created kind before restoring the old one. Extend
`a_native_push_rolled_back_puts_home_back_exactly` with all five cases.

### M2. Receiver containment holds only against an honest peer (class 2)
`src/native/receive.rs:37,109-133,185,222-223`, `src/native/backup.rs:47-55`, `src/native/workers.rs:179-190`.

`rel` itself cannot escape: `..`, absolute, `.`, empty components, a trailing slash,
NUL and symlinked ancestors are all refused (`p17`, `nothing_is_written_through…`).
But a peer holding a pinned certificate can get out of the unit by sequencing
frames. All reproduced with frames on `serve::answer`:

- **`p06` stale `real` cache.** `Mkdirs a`; file `a/x`; `Replace a`; symlink
  `a → /outside`; file `a/pwned`. The cache still says `a` is real, so the file
  lands in `/outside`. `real` is never invalidated.
- **`p07` `dir_modes` follows a link.** `DirModes [l]` with `l → /outside` chmods
  `/outside` to 0777: `path()` checks parents only, and `set_permissions` follows.
- **`p08` backup follows a link it kept.** Replace symlink `a → /outside` (kept as
  `run/a`), then write `a/x` twice. The second `keep` resolves through `run/a` and
  renames the file to `/outside/x`.
- **`p09` a pull trusts the entry, not the request.** Home answers `Get ["asked"]`
  with an entry for `leaf-only.txt`, and the leaf overwrites it (`Ok(())`). This is
  the class-1 outcome if home is ever wrong.

I found no honest sequence that reaches these: the source cannot list children under
a path that is a link. A local process swapping a directory for a link mid-transfer
reaches the same code (agents work on home), but only as a narrow race.

**Fix:** drop `real` or clear it on any removal; `lstat` the final component in
`dir_modes`; refuse a backup destination with a non-directory ancestor; in
`workers::pull`, refuse any entry not in `asked`.

### M3. An interrupted repo pull can block its own resume
`src/native/workers.rs:60-65`, `src/guard.rs:79`.

`.git/index` goes in round one and sorts ahead of the worktree. Cut between them
and the index says the new content while the worktree file is old: `git status`
says dirty, and that path is still to be sent, so guardrail 1 refuses.

**Reproduced by placing that state** (`h1`: objects and index from home, `README`
not yet; I did not time a real cut to land there): `Blocked { guardrail 1 (dirty
target): work/alpha }`. It fails safe, but the person must work out that a
`git checkout` of a file they never touched is the way out. Batches make this a
multi-batch case; the push mirror on home is the same logic (inspection). rsync's
order had the same hole (inspection); `guard.rs` changed only in wording.

**Fix:** put `.git/index` in the refs round. Arrived files are then dirty but no
longer touched, and files not yet arrived are clean, so the guardrail does not fire.

### M4. Core invariants have no behavioural test
Each mutant below passes the existing 565. For each I demonstrated a difference
with a differential test that passes on the branch and fails on the mutant,
except M5, which rests on `p18` (below).

| Mutant | Existing 565 | Differential | Requirement left unguarded |
|---|---|---|---|
| Push deletions before sends | pass | fails | deletes only after sends |
| Pull deletions before sends, **moved** | pass (a mutant that added a second call tripped only the text gate) | fails | same |
| Push refs round first | pass | fails | refs last |
| Push no longer compares to the plan | pass | fails (`Done` vs `Failed`) | "a push changed since the plan" row of the failure table |
| No socket write timeout | pass | not run on the mutant; `p18` depends on it | dead-peer write |

Pull refs-first was caught only incidentally, by `a_killed_transfer…`. The three
differential tests are about 15 lines each; adopt them, plus `p18`.

## Minor

- **m1. Existing read-only target dir whose source is writable never fills.**
  `receive.rs:206` returns early for an existing directory, though `frame.rs:43` says
  "create or chmod"; the mode only changes in the final round. `p15`: permanent
  `Permission denied`. Chmod existing directories to `mode | 0700` in `mkdir`.
- **m2. Errors name no path.** `p15`'s whole message is `transfer: io: Permission
  denied (os error 13)`, on what could be a 70k-file unit. Wrap the fs calls in
  `receive*.rs` with `rel`.
- **m3. Case-only rename onto APFS deletes what just arrived.** Home `foo.txt`, leaf
  `FOO.txt`: the diff says send one and delete the other, and the delete resolves to
  the new file (`p16`). First run fails verification with the file absent, second
  completes. Guardrail 4 sees collisions inside home only. Extend it across source
  and target names. A directory rename where the old directory also holds an
  excluded path may never converge (inspection, not run).
- **m4. Verification passes while a link differs.** `manifest.rs:71` is lossy: a
  non-UTF-8 link target arrives altered and both sides compare equal (`p20`: source
  `caf\xE9/x`, home `caf\u{FFFD}/x`, `ok=true`). Same family: non-UTF-8 names are
  skipped silently, subtree included (`manifest.rs:201`, consistent with discovery).
  Refuse or note them.
- **m5. The baseline can land before home's names are durable.** `Done` has no ack
  (`serve.rs:68-70`, `transfer_run.rs:214-216`), so the leaf verifies and writes
  baselines while `sync_dirs` may still run. Also `receive.rs:267-269` ignores fsync
  errors, and `replace`'s removals are not touched (`:185,:197`). Power loss on home
  in that window reverts names against a baseline saying they agreed, and the next
  plan reads "home changed → pull", the wrong direction. Inspection only, narrow, and
  still better than rsync's no-fsync. Ack `Done` after `sync_dirs`.
- **m6. A home write has a third state.** `receive_file.rs:90-95` displaces, then
  renames: a crash or failed rename between them leaves the target **absent** (the
  original is in `backup/`, and a resume repairs it). The notes' "the source's or the
  target's old one" omits this. `hard_link` into the backup, then rename over, closes
  it with no copy (fall back on `EXDEV`).
- **m7. A partial `EXDEV` copy looks like a kept file.** `backup.rs:86` copies straight
  to the final name. A failed or crashed copy leaves a truncated file that `kept()`
  reports, and rollback would restore it over the intact original. Inspection, not
  run. Copy to a temp name and rename.
- **m8. The ack timeout also times the work.** A frame is acked after its whole list
  (`serve.rs:108-111`). A `FileEnd` fsync, a huge `Deletes`, or an `EXDEV` copy over
  60 s reads as a dead peer, and the same file can fail every run on a slow disk.
  Home keeps writing until that frame ends. Bounded, and only home's next frame is
  refused. Inspection. Splitting lists (B3) reduces it.
- **m9. Write-set gate gaps.** Planted and **not** caught: `File::create_new(`,
  `f.set_len(0)`, `os::unix::fs::chown(`, `lchown(`. Add them to `PATTERNS`.

## Nits

- `receive_file.rs:133`: `take()` before the fallible steps, so a failed fsync leaks the
  temp until the next run.
- `manifest.rs:137-142`: a single-file unit never collects its temp.
- `serve.rs:7` and PLAN "before every frame": on a pull, the lease is checked per `Get`,
  not per chunk (`serve_pull.rs:25`). Read-only, so harmless, but the claim is wider
  than the code.
- `.replicant-tmp-*` is a reserved name: `p21` shows a real file so named on the target
  is removed without a backup. Say so in Known limits.

## Verified OK: the twelve items

1. **Receiver containment: holds for an honest peer; see M2 for a hostile one.** `..`,
   absolute, NUL, `.`, empty components and symlinked ancestors are refused (`p17`,
   mutant caught). Writes never follow a link: `create_new` temp, rename and unlink
   do not follow; deletes `lstat` first. Temp collisions: one name per target, each
   file on one worker. Case-fold temp collision is reachable only past guardrail 4
   (inspection). Exception: m3.
2. **Sender read-only on a push: yes.** The push path never opens a `Receiver`
   (`transfer_run.rs:164-236`). `source.rs` opens read-only with `O_NOFOLLOW`. git runs
   with `--no-optional-locks`. `Clean` goes to the target only. Fingerprint test passes;
   a planted write in `source.rs` or `workers.rs` turns the gate red.
3. **Ordering: correct.** Deletes after both rounds; dirs before children; refs last.
   A `.git` without `HEAD` is not a repo: `h3` resumes with no refusal, and `h2` (`HEAD`
   present, refs not; `git status` exit 0, unborn) resumes too. Two exceptions: `Replace`'s
   `under` deletions must precede sends (confirmed plan, backed up on home), and they
   run before a kept directory refuses. Not tested behaviourally: M4. Blocked resume: M3.
4. **Atomicity: order correct.** `receive_file.rs:135-140`: mode, mtime, `fsync(2)`, close,
   rename. The final name never carries a wrong mtime.

   **Crash-safety claim, precisely:**
   - *Process death, any platform:* the final name is old or whole. No torn file, and a
     temp is cleaned next run. (On home, also possibly absent: m6.)
   - *Power loss on Linux:* `fsync` issues the cache flush, so a renamed file's bytes are
     durable; the rename itself may revert until the journal commits (m5).
   - *Kernel panic on macOS:* the drive keeps power, so same as above.
   - *Power loss on macOS:* no drive-cache barrier. A file can survive under its final
     name with the right size and mtime and wrong bytes.

   That last case is the catch: **"the source still holds it" does not help, because
   nothing looks.** Diff and hash read metadata, so it stays wrong. Not tested (no
   power-cut rig). **Acceptable for 0.4:** rsync never fsynced at all, the macOS side is
   a laptop with a battery, and home is Linux. PLAN's Known limits should state the
   undetected consequence. One `F_FULLFSYNC` per unit before the baseline flushes the
   whole drive cache at about 4 ms a unit, which would give the baseline a real durability
   point without the per-file cost.
5. **Interrupted mid-unit: holds.** Whole files only, marker kept, no baseline, temps
   cleaned, resume skips identical files (fault tests; mutant M14 caught). After an abort,
   workers stop at the next item; a batch in hand finishes, whole. Home stops at its next
   frame. Old-thread race: a late `Drop` can unlink a new run's temp, which fails loudly at
   rename and never installs a partial (inspection). Exceptions: M3, B2 (FIFO), B3.
6. **Verification: correct on what it compares.** Size, mtime_ns, mode, kind and link are
   compared both ways; only `Ran::ok` reaches a baseline; mutant caught. Rehash/Agree are
   unchanged. Baseline written with trees differing: only m4's lossy links and skipped
   names, plus kept directories by design and the Known-limits items.
7. **Backup by rename: holds; round trip does not (M1).** `EXDEV` fallback works with
   metadata (test via stand-in rename; m7 for partial). Sweep unchanged (`home_sweep.rs` has
   no diff) and only `remove_dir_all`s `backup/<host>/<id>`. Home's only renames: temp to
   target in one directory, and target to `backup/`; except `p08` under M2.
8. **Stall, abort, dead peer: holds.** Production `Conn` sets `SO_SNDTIMEO` and `SO_RCVTIMEO`
   on the socket under TLS. `p18`: a blocked TCP write to a silent peer fails at the timeout,
   with no shutdown involved. `p19`: shutdown wakes a blocked writer on macOS TCP (`Broken
   pipe` at 1.0 s), and the timeout backstops it if it ever did not, so no dependence on the
   fixture's `ENOTCONN` quirk. `p22`, real mTLS: four home writers stuck on a silent leaf
   held all stream slots and a fifth was refused; slots returned after 13 s at a 1 s ack
   timeout (not broken down). The timed write probes are plain TCP through production
   `Conn`; TLS is by `p22` and inspection. Heartbeat runs on its own thread and link
   (`lease.rs:120-125`), which is also why B2 and B3 hold the queue.

   guard weakened.
