## Verdict

**Merge.** Nothing on this branch writes to either tree, changes rsync
arguments, or changes the write set. Ctrl-C mid-unit leaves exactly what a
lost lease leaves. One Minor finding: in a narrow window (P1), an abort lands
after the between-units check but before the marker. The result is still the

## Findings

### P1 (Minor): an abort raised during `UnitStarted` still writes the marker and starts the rsync

`src/plan/apply_each.rs:60-91`. The loop checks the abort (line 60), then
emits `UnitStarted` (line 73), then calls `transfer`, which writes the pull
marker (`apply_unit.rs:88-97`) and spawns rsync. `child::run` spawns before it
looks at the flag (`rsync/child.rs:119-134`), so rsync then gets SIGTERM.

- **Realistic trigger.** The builder's own "Observed, not fixed" case. A CLI
  is suspended (Ctrl-Z) or its terminal is paused (Ctrl-S), so the socket
  buffer fills and the daemon blocks in `send` of beta's `UnitStarted`. The
  person then kills the CLI. The write returns EPIPE and
  `local.rs:watched/emit` raises the abort, or the watch thread sees EOF while
  the write is blocked. `emit` returns and the unit goes ahead.
- **Reproduced.** In an isolated copy (`/tmp/repl_probe`, `git archive
  HEAD`) I ran a probe test using the `sync_watched` helper that raises
  `HANGUP` on beta's `UnitStarted`. Result: `Interrupted { rel: "work/beta",
  why: "the CLI hung up …; rsync stopped", journaled: true }`, with the marker
  `work/beta` present. `docs/v0.2-prep-notes.md:1006` and the `apply_each.rs`
  and `progress.rs` docs say a hangup between units means "the next never
  begins … nothing of it written, not even a marker".
- **Impact.** This is not data loss. It is the lost-lease mid-unit state: the
  marker is kept, no baseline is written, the event is journaled
  `interrupted`, the next `sync` resumes, and guardrail 6 protects leaf work
  newer than the marker. But it is a needless marker, plus a few ms of real
  rsync (a pull, or a confirmed `delete here`, can partly land). It also
  breaks a promise the docs make. The same window existed for a lost lease
  before; the blocking emit widens it from microseconds to "as long as the
  CLI is stopped".
- **Fix.** Check `watch.abort().raised()` again after the `UnitStarted`
  emit. If it is raised, emit that unit's `UnitDone` with
  `stopped_before(u, watch)` and return it. Better still, check before the
  marker inside `transfer` (pull) and before `BeginPush` (push), so the
  confirm-delete `Note` round-trip is covered too. Add a test that raises on
  `UnitStarted` (the probe above, asserting no marker).

### P2 (Minor, test gap): hangup after rsync exit 0 is untested

Inspection shows the right behaviour, and better than a lost lease. After
`ran.ok()`, `transfer` consults only `watch.check()`, which looks at the lease
alone (`apply_unit.rs:160`). `after()` rehashes locally or via home `Rehash`
and does not use the `Runner`. So a hangup that lands between rsync exit 0 and
the baselines lets the unit finish (baselines, marker cleared, `Settle`). The
next loop pass then stops before the following unit. No test pins this. A
plausible "tightening" that adds `|| watch.abort().raised()` at line 160
would turn a finished transfer into a kept marker plus a resume, and every
current test would still pass. The existing `apply_progress_tests.rs:181`
raises only after `UnitDone`, which is after `Settle`. Suggested test: a fake
rsync wrapper that exits 0 after signalling, with the abort raised from the
test before `transfer` returns. Alternatively, a doc line at
`apply_unit.rs:158` saying why the post-exit check is lease-only.

No other findings.

## Verified OK (the seven items)

1. **No new writes, rsync args or write-set change.** I read `git diff
   main...HEAD -- src`. New code adds no `put`, `delete`, `fs::`,
   `File::create` or argument changes (grep over the added lines found
   none). `rsync.rs` changes only the stop message; `child.rs` changes only
   `Abort`. `apply_gate.rs` and `leaf_status.rs` are pure moves: every
   non-header line matches the main versions. The one change in the apply
   loop is that each unit's `step` and baseline read are now precomputed. That
   is order-preserving and pure (`apply_step.rs`), and a baseline read error
   still fails at its own unit.
2. **Hangup mid-unit is identical to a lost lease.** The marker is kept on the
   target, no baseline is written, `Interrupted` is journaled, later units are
   untouched, and the next sync resumes. `apply_hangup_tests.rs` checks all of
   this via `stopped_at_beta` and `resumes`. It does not void the plan:
   finished units stand, the entry is released, and the report goes home.
   - **No spurious fires.** The watch raises only on EOF or a hard read error.
     `WouldBlock`, `TimedOut` and `Interrupted` are ignored, and incoming data
     is ignored. The CLI never half-closes, and it is the only in-tree client
     (`local.rs:47`; `mod.rs:151` is the listener's wake-up). A slow reader
     never raises: writes have no send timeout, so they block rather than
     fail.
   - **SIGPIPE.** `main.rs:11` resets SIGPIPE to SIG_DFL for the daemon too,
     but std's `UnixStream` write uses `MSG_NOSIGNAL` (Linux) and SO_NOSIGPIPE
     (macOS). I checked this in the rust-src of the installed toolchain and
     probed it on macOS: the write gets `BrokenPipe`, the process survives.
   - **The CLI's own stdout or stderr closing** is best-effort and ignored
     (`cli/sync.rs`), so the CLI keeps reading and the sync is not aborted.
   - **After rsync exit 0:** the unit finishes (see P2).
3. **Streaming changes no semantics.**
   - The gate is a pure move.
   - `SyncOpts` (`--yes`, `--confirm-delete`, `--accept-rollback`, `expect`)
     is untouched.
   - Plan order is unchanged.
   - `plan()` (dry run and `status`) passes a default abort and emits
     nothing. `daemon_progress_tests.rs` checks that neither emits frames.
   - A hangup during a dry run does not stop it. That is harmless (read-only),
     but the dry run then runs to completion.
4. **Backpressure.** `emit` writes synchronously on the apply thread, but
   only at unit boundaries: before the marker and after `Settle`, never
   mid-rsync. The heartbeat is its own scoped thread (`lease.rs:119-124`), so
   a stalled CLI pauses apply without losing the lease. Accepted per the
   brief. The side effect is that home's queue is held for as long as the
   terminal stays paused; the builder's notes already record this.
5. **EPIPE on a frame write raises the abort** (`local.rs` `emit`), with the
   same `HANGUP` reason. It is not ignored.
6. **Reason-carrying abort.** The first raiser wins, and `raise` and
   `raise_because` serialize on the same mutex. Only the message differs:
   - `stopped_before` prefers the lease error.
   - `transfer` uses the hangup reason only when the abort carries one,
     which means the hangup came first and killed rsync before any lease
     loss. That is the accurate cause.
   - A later lease loss still fails `run` via `watch.check()`, and
     `sync_with` keeps the `Interrupted` outcome.
   - Behaviour is identical either way.
7. **Tests.** The hangup test kills a real running child (a fake rsync wrapper
   whose pid and grandchild pid are both checked as gone), uses the real
   `local::serve`, and is bounded at 20 s against a 30 s sleep. All the new
   tests I read use `Bed` or `tempdir`, or socket pairs. None of them touches
   a real home or work tree.

## Context (not findings)

- **`--json` output changed shape.** At a terminal, stdout is now NDJSON
  (events, then a one-line report) where it used to be one pretty object.
  Anyone parsing it as a single document breaks. That makes this a
  0.BREAKING change, so 0.3.0, which the branch name already implies. The
  local wire is bumped to 5 and kept separate from the home↔leaf
  `WIRE_VERSION`, and both version-mismatch directions read correctly.
- **Lost lease between units.** It now stops before the next unit's marker
  as well (it used to write the marker, then kill the rsync). That is a
  strictly safer change, and it is documented.
