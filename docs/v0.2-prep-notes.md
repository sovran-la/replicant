# v0.2-prep notes

Two changes to the walk/exclude layer on `bsneed/v0.2-prep`, one commit each.

## 1. Exclude engine: globset (`ee075bf`)

`src/exclude.rs` no longer hand-rolls rsync's matcher. Patterns are globset
0.4.20 globs (the version `sovran.la/filesystem` locks) built with
`literal_separator(true)`, so `*` stays inside one component as it does in
rsync. The matching rule is the filesystem crate's `WalkOptions::is_excluded`:
a pattern matches the **unit-relative path** or the **bare file name**.

**Not adopted: the absolute-path arm.** The filesystem crate also tries the
absolute path. In replicant one unit is `/Users/morgan/...` on a Mac and
`/home/morgan/...` on Linux, and rsync only sees paths below the transfer
root, so an absolute match would make the two sides and rsync disagree.

Each pattern is parsed once (`src/exclude/pattern.rs`) and both the glob and
the rsync rules are rendered from the same tokens. `Excludes::new`,
`for_root` and `push` now return `Result`; `matches`, `path_excluded`,
`push_exact` and `rsync_args` keep their signatures. fleet.toml patterns are
checked at load (`exclude::check`), so a bad pattern fails `fleet.toml`, not a
sync.

### Behaviour changes

- A pattern with an inner `/` (`agents/state`) is now **rooted at the unit**,
  as the filesystem rule makes it. It used to match at any depth (rsync's
  unanchored rule). To match at any depth, write `**/agents/state`. PLAN.md's
  example config is still valid; a one-line comment there now says this.
- The built-ins are `**/.git/**/*.lock` and `**/.git/worktrees/` (they were
  `.git/**.lock` and `.git/worktrees/`). They mean the same thing, at any depth.
- Patterns the old matcher accepted but that are now refused (see below)
  make fleet.toml fail to load. A leaf running this code against an older home
  that sends such a pattern fails at discovery. Upgrade both ends together.

### Translation table (globset → rsync)

| globset (fleet.toml) | means | rsync rule(s) |
|---|---|---|
| `target` | name, any depth | `target` |
| `*.log` | name, any depth | `*.log` |
| `build/` | directory name, any depth | `build/` |
| `/top` (internal only) | unit-relative path | `/top` |
| `agents/state` | unit-relative path | `/agents/state` |
| `a/**` | everything under `a` (not `a`) | `/a/**` |
| `**` | everything | `/**` |
| `**/x` | `x` at any depth | `/x`, `/**/x` |
| `a/**/b/` | `a/b`, `a/…/b`, directories | `/a/b/`, `/a/**/b/` |
| `**/.git/**/*.lock` | two `**/` → four rules | `/.git/*.lock`, `/**/.git/*.lock`, `/.git/**/*.lock`, `/**/.git/**/*.lock` |
| `v[0-9]` | positive ASCII class | `v[0-9]` |
| `\*lit` | literal `*` | `\*lit` |
| `we\\ird` (no wildcard) | literal `\` | `we\ird` (rsync treats `\` as an escape only when the rule has `*`, `?` or `[`) |
| `we\\ird*` | literal `\`, then `*` | `we\\ird*` |
| `\{x\}` | literal braces | `{x}` |

Why the expansion: globset's `**/` matches zero or more directories, but
openrsync's matches one or more (measured: `/a/**/b` does not exclude `a/b`).
Each `**/` therefore becomes a rule without it and a rule with it. At most
four `**/` per pattern (16 rules).

`rsync_rules_follow_the_translation_table` in `src/exclude_tests.rs` holds the
code to this table.

### Refused, and why

| Pattern | Reason |
|---|---|
| `?` | globset matches one character, rsync one **byte**: `q?` excludes `qé` in globset, not in openrsync (measured) |
| `[!a]`, `[^a]` | same character/byte split. openrsync also does not support `^` at all: `q[^a]` did not exclude `q1` (measured) |
| non-ASCII, `/`, `\`, `[` (so `[[:alpha:]]`) inside a class; `[]…]`; `-` at a class end; bad ranges | the two engines read these differently, or not at all |
| `{a,b}`, unescaped `{` `}` | alternation exists only in globset. `\{` is accepted |
| `**` inside a component (`a**`, `.git/**.lock`) | globset reads it as `*`; rsync's crosses `/` |
| `***` | rsync-only syntax |
| `//`, `\/`, trailing `\`, unterminated `[`, unmatched `]` | malformed. The old matcher treated an unterminated `[` as a literal; globset refuses it |
| empty, `/`, leading or trailing whitespace, line breaks | they name nothing, or rsync would trim or split them |
| `!`, `+ …`, `- …` | rsync reads them as filter-rule prefixes (`!` clears the list) |
| anchored `/x` in fleet.toml | still refused, as in v0.1. Used only internally by `push_exact` |

### Differential test

`src/exclude/rsync_diff_tests.rs` builds an 80-entry fixture: repeated names
at several depths, `.git` at the root and nested, a symlink to a directory,
names with `\`, `*`, a space and braces. For each pattern class (bare name,
`*.ext`, `dir/`, anchored `/x`, `a/**/b`, rooted and `**/`-prefixed slash
paths, `x/**`, classes, escapes, `**`, built-ins, `push_exact` literals, a
whole root list) it asserts that the set `path_excluded` drops equals the set
`rsync -n -a -8 --itemize-changes` leaves out given `rsync_args()`, and that it
equals a hand-written expected set. It also checks `repos::all_names`, a real
walker, against rsync. It runs against the system rsync and names the flavour
on failure. Here that is openrsync (protocol 29). As a check, breaking the
`**/` expansion makes 4 of its 6 tests fail.

## 2. Parallel discovery (`7204cbd`)

`repos::discover` now walks with `ignore::WalkBuilder::build_parallel()`
(0.4.33, as the filesystem crate locks it). Every ignore source is off
(`hidden`, `git_ignore`, `git_global`, `git_exclude`, `ignore`, `parents`,
`require_git`) and so is `follow_links`. The walk uses `state::workers()`
threads. Each thread keeps its findings and sends them down an `mpsc` channel
when it is dropped. `discover` sorts every list, as before. Code:
`src/repos/walk.rs`.

What is unchanged: repos (`.git` dir) and worktrees (`.git` file into
`.git/worktrees/`) are recorded and not descended, excludes prune
directories, non-UTF-8 names are skipped, and an unreadable directory is an
`Error::Io`. `all_names` (the case walk, which skips `.git/objects`) is still
serial; it already runs per unit inside `parallel_map`.

Tests (`src/repos/walk_tests.rs`):
- the old serial walk, kept as a reference, equals the parallel one under
  three exclude lists;
- five discoveries of an 800-file tree are identical;
- hidden files and files named in `.gitignore`, `.ignore` and `.rgignore`
  are all seen;
- deep worktrees and repo-in-repo are not descended;
- a repo under an excluded directory is not found;
- an unreadable directory is an error.

Removing the sort makes three of them fail.

## Noticed, not fixed

- **The parallel walk has a fixed cost**: about 3 ms per `discover` in release
  and 4–7 ms in debug, even on a tiny tree. Most of it is likely `ignore`'s
  idle workers waiting before they quit. The cost is paid once per
  subscription. If a host has many small subscriptions, `Discovered::run`
  could do one multi-root walk (`WalkBuilder::add`) instead of one walk each.
- **Not verified against rsync 3.** This agent had no tailscale access, so the
  differential test has only run against openrsync. The translation uses only
  what both read the same way (anchored rules, and a `**/` rule plus its
  zero-directory twin). Run `cargo test exclude::rsync_diff` on thistledown to
  confirm.
- **Pre-existing drift, now gone.**
  - Under openrsync the old unanchored built-in `.git/**.lock` matched only a
    `.git` at the transfer root: `r/.git/HEAD.lock` was not excluded.
  - The old `push_exact` escaped a `\` in a name even when the rule had no
    wildcard, so rsync matched the name literally and missed it.
  - The old `[^…]` class does nothing in openrsync.
- **Root excludes are relative to each unit.** A slash pattern therefore
  covers different paths depending on how a host's subscription is split:
  `tundra/x` matches under a `work` subscription but not under `work/tundra`.
  This was true before, and the rooted rule makes it sharper. `**/` patterns
  do not have the problem.
- **Mixed versions.** An old leaf reads `**/x` with the old matcher, which
  needs a `/` before `x`, so it misses a top-level `x`. Upgrade home and every
  leaf together.

# v0.1 review fixes

Five items from `docs/v0.1-review.md`, one commit each, regression test
first. Baseline before the first one: 260 tests, clippy and fmt clean.

## Nit: `for-each-ref` decoded strictly

`git::decode_refs` replaces the lossy decode in `git::status`. A ref name that
is not UTF-8 is an `Error::Git` naming the repo and the ref, the same shape as
the porcelain decode (`parse_porcelain_v2`), which already refused paths.

Tests (`src/git_tests.rs`): the decoder directly, and real git. APFS refuses a
non-UTF-8 file name, so `git update-ref` (with `--stdin -z`) fails here with
EILSEQ before it writes anything; a hand-written `.git/packed-refs` line gets
the byte `0xE9` through `git for-each-ref`, and `status` must refuse it. Both
tests failed against the old lossy decode.

## Q3: `refs/remotes/*` left out of the repo hash

`state::repo` hashes every `for-each-ref` line except those starting with
`refs/remotes/`. Branches, tags, `refs/stash`, HEAD and anything else (notes,
replace refs) are still hashed. The module doc records it as a decision.

For a repo with no remote-tracking refs the hashed bytes are unchanged (each
line is fed back with its `\n`), so its hash is the same as before. A repo
with remote-tracking refs hashes differently from v0.1. No production
baselines exist yet (v0.1 is read-only), so nothing is invalidated.

Test (`src/state_tests.rs`,
`remote_tracking_refs_are_not_state_but_local_refs_are`): creating, moving and
packing remote-tracking refs leaves the hash alone; creating and moving a
local branch, adding a tag, and a local branch literally named
`refs/heads/refs/remotes/x` all change it. It failed on the first
remote-tracking ref before the change.

## F11: hand edits to fleet.toml are honored

`Home` keeps the parsed `Fleet` in `daemon/home_fleet.rs` (`FleetCache`).
Every look at it (`Home::fleet()`, which every fleet-dependent request and
`approve`/`preview_allow`/`pending` go through) stats fleet.toml first and
reloads when its mtime, size, device or inode differ from the last load. The
stat comes before the read, so an edit landing between them is picked up on
the next look. Home's own writes still reload under the same lock, and that
reload records the new stamp, so they do not log a spurious "changed".

A reload that fails is an error for the request, naming the file, and stays
one until the file parses: the stale fleet is never served instead, so a cap
narrowed with a typo cannot fall back to the wider cap. Consequence: while
fleet.toml is broken, `Heartbeat` fails too (it reads the lease length), so a
dry run in flight loses its lease. That is the conservative failure; noted
here so it is not a surprise. `Release` does not read the fleet and still
works. `Home::name`, `Home::pending` and `Home::view` became fallible for
this; the local `Ping` now reports a broken fleet.toml.

Tests (`src/daemon/home_reload_tests.rs`, against a running `Home`, editing
the file in place):
- a cap narrowed by hand bounds `Subscriptions`, `State` and the queue
  entry `Acquire` takes, on the very next request;
- a same-size edit is seen through its mtime;
- a pending host and a root added by hand show in `pending`, `preview_allow`
  and `approve`, and the approve write keeps the hand edit;
- a broken edit refuses requests (twice: the stale cache does not return),
  and fixing it recovers;
- home's own `Unsubscribe` write is still seen.

The first four failed before the change (the fifth is a guard against
regressing the own-write path).

## Found on the way: `write_atomic` raced itself (not a review item)

`config::write_atomic` named its temporary `<file>.tmp.<pid>`, so two
threads of one daemon writing the same file shared it: the first rename
moved it away and the second failed with ENOENT. Home's request threads do
exactly that: every request `fleet::touch`es the caller's contact record,
and a leaf's heartbeat thread runs alongside its `State` call. The F8
end-to-end test hit it. The name now carries a process-wide counter too.
Test: `config::tests::concurrent_writers_of_one_file_do_not_collide` (8
threads × 200 writes to one path), which failed with ENOENT before.

## F8: a waiter's lease lives only while its connection does

`Queue::acquire` is now `enqueue` + `wait` (`acquire` remains, for callers
that cannot tell, and always says "connected"). `wait` takes a `connected`
probe and asks it once per tick, under the queue lock:
- connected: the waiting entry's lease is refreshed, as before;
- not connected: it is not refreshed, so the reaper's next sweep after the
  lease runs out expires it and journals `expired`, as for a dead head;
- not connected and at the head (the head was released before the sweep):
  withdrawn there instead of being granted a lease nobody would heartbeat.
  Home journals that as `expired` too (`WAITER_GONE`).

Home's mTLS request thread passes `remote::connected(&sock)`: a
non-blocking one-byte `peek` on the TCP socket, with blocking mode restored.
EOF (FIN, or RST) or an error means the leaf is gone; would-block or bytes
waiting mean it is still there. `Home::handle` keeps its signature (always
connected) and `Home::handle_from` takes the probe.

Tests:
- `src/daemon/queue_waiter_tests.rs` (the probe is a flag, and reports the
  instant of each call, so expiry is checked against those instants, not
  sleeps): a disconnected waiter is expired by the sweep and never started;
  connected, it was alive past the probe; one that reaches the head while
  disconnected is withdrawn and the entry behind it (30s leases) proceeds at
  once; a disconnected caller is not granted even an empty queue. All three
  failed before (the old loop never consulted the connection).
- `remote_tests::connected_sees_a_peer_leave_and_leaves_the_socket_blocking`:
  real loopback sockets: idle peer connected, pending bytes connected and not
  consumed, `O_NONBLOCK` cleared afterwards, closed peer gone.
- `src/daemon/daemon_queue_tests.rs`: a real home daemon with 1s leases; a
  leaf holds the head (heartbeating), a second leaf call waits and its client
  gives up after 2.5s. The waiter is still queued at that moment (kept alive
  past two leases while connected), then is expired by the reaper, journaled
  as `expired … waiting`, and the head is untouched. With the TCP loop
  reverted to `Home::handle` it fails: the dead waiter is still queued after
  10s.

### Observed, not fixed

- **A leaf that vanishes without a FIN** (power cut, partition) still reads
  as connected; its waiting entry lives until `MAX_QUEUE_WAIT` (10 min), as
  before. TCP keepalive on the accepted socket (via `libc`, already a
  dependency; `TCP_KEEPALIVE` on macOS, `TCP_KEEPIDLE` on Linux) would bound
  it; left out to keep this change small. A waiter-side heartbeat would
  need a wire change (the waiter does not know its id until `Acquire`
  returns).
- A peer that sent bytes while waiting reads as connected even after its FIN,
  because the peek sees the bytes first. The leaf sends nothing while it
  waits (one request per connection, no TLS close_notify from the client),
  so this does not arise today.
- The waiter's lease is the fleet's lease at enqueue time; a hand edit to
  `lease_secs` applies to the next `Acquire`, not to entries already waiting.

## F4: a vanished unit is never a silent delete

Preceded by a no-behaviour refactor (`units.rs` was 313 lines): the per-side
snapshot moved to `src/units/snapshot.rs`.

### (a) A missing base is an error

`repos::discover` still reports a missing base as `exists: false`. It cannot
apply the policy itself, because only the leaf holds the baselines. The rule
is in the `repos` module doc and is applied in `src/plan/bases.rs`:

- **Leaf**: a subscription whose local path (identity or `--as`) does not
  exist is `Error::Missing`, "subscription base /x does not exist on leaf,
  but work/r was synced there (a baseline exists); restore it or change the
  subscription". The one exception is when no baseline lies under it
  (`paths::is_within(baseline, sub)`): that is the first pull. The check
  runs before `Acquire`, so a refused dry run never queues.
- **Home, root**: if a served subscription's root path is missing, home's
  `State` fails with "root work (/path) does not exist on home", always, even
  on a first sync.
- **Home, base below a root**: home lists such subscriptions in the new
  `HomeSnapshot.absent` (`#[serde(default)]`, so wire version 1 still reads
  both ways). The leaf applies the same baseline rule with home's name and
  path. With no baseline, it is the first push.

New `Error::Missing` variant ("missing: …"). `status` and `sync --dry-run` both
fail with it, since they share `plan::plan`.

### (b) `Decision::DeletedOn { host }`

The row is carved out of "home changed, leaf same" and "home same, leaf
changed" only: Present at baseline, Empty now on `host`, and the other side
unchanged and non-empty. Every other row is untouched. Vanished on one side
and changed on the other is still a conflict; gone on both is still "both
changed identically"; Empty at baseline is still a pull or push. It
`is_blocking` (red; `blocked()`, so exit 2) and has **no `direction()`**, so a
future apply has nothing to carry out without a confirmation flag. Neither the
flag nor apply is implemented.

Rendering: the unit line's label is `deleted on X`. Under it, in red,
`PlannedUnit::deletion_note` prints "deleted on X — would remove N files on
Y; requires explicit confirmation" (`1 file` in the singular). The summary
line is `deleted, needs confirmation: N units`. On a dry run the unit is also
diffed with rsync in the direction its deletion would travel (toward Y,
`plan::diff::diff_direction`), and guardrails run as usual, so guardrail 1
names Y's uncommitted work.

N is `SideUnit::files` (new, `#[serde(default)]`), counted by each side for
itself: for a repo, index entries (read from the `.git/index` header by
`git::index_entries`, with no extra git process) plus untracked entries; for
loose content, non-directory entries. `.git` itself is not counted, so N is
smaller than the rsync diff's deletion count, which includes `.git`.
`PlannedUnit` carries both sides' counts (`leaf_files`, `home_files`).

`decide::Inputs` gained `home_name`.

# Pre-merge fixes (from `docs/v0.2-prep-review.md`)

## P2: a class range spanning `/` is refused (`P2:` commit after `8e4fd9d`)

`pattern::class` refused a literal `/` but not a range containing 0x2F
(`[+-0]`, `[.-0]`, `[ -~]`), which globset matches across components and rsync
never does. Such a range is now a config-load error ("spans `/`"). Tests:
`exclude_tests.rs::class_ranges_spanning_the_separator_are_refused` (refusals
plus the neighbours `[#-.]`, `[0-9]` still accepted) and
`exclude/rsync_diff_class_tests.rs` (`x/a[+-0]b` refused; `x/a[0-9]b`,
`x/a[#-.]b`, `x/a[*-.0-9]b` agree with rsync; fixture gains `x/a.b`, `x/a0b`).

`rsync_diff_tests.rs` (315 lines before) and `exclude_tests.rs` are now a
little over 300; the new cases went into new files where they could.

## F5: `Remove` is narrow (`5b9ac13`, amended in `66f2036`)

**What changed.** Home remembers what `unsubscribe` removed
(`[subscriptions.x] unsubscribed`, cleared for whatever a later `subscribe`
restores); a carve-out was already in `except`. The leaf sends its baseline
paths with `State` (`baselines`, serde default) and home answers
`HomeSnapshot.unserved`: per path, the spec home would apply to it
(excludes, carve-outs, root) and a reason (`Unsubscribed`, `CapNarrowed`,
`RootMissing`, `Excluded`, `NotServed`), checked non-explicit reasons first,
so a cap narrowed over a carve-out is still "cap narrowed". The leaf hashes
its copy with that spec (`plan/unserved.rs`) and `decide::decide_unserved`
picks the row:

| case | row | blocks |
|---|---|---|
| marker over it (either side) | conflict naming the interrupted sync | yes |
| unsubscribed, leaf == baseline.leaf | `Remove` | no |
| unsubscribed, leaf changed | conflict: "push first, or `replicant unsubscribe --force <path>`" | yes |
| cap narrowed / excluded / not served | `Orphaned { reason, changed }`: dim, red if changed | no |
| root missing on home | `HomeRootMissing`: "home's root for … is missing or renamed (…); fix fleet.toml on home" | yes |

The first commit made every non-Remove case a blocking conflict, as first
briefed; Brandon's amendment (received mid-task, after `5b9ac13` was
committed) weighted them, so it landed as its own commit rather than an
amend. With it, the cap-narrowed and excluded *subscriptions* moved from
`refused` (blocking) to a new `orphaned` list (`SubscriptionsView`, `Plan`;
rendered dim, not blocking); a subscription whose root is gone stays
refused. `Excluded` (from P3) is weighted like a narrowed cap: it is home's
policy, not a broken config. That was my call.

**Found on the way:** a loose unit's `Remove` diffed with no excludes at
all, so removing `work/b` would have `--delete`d every repo inside it,
including one in conflict. The diff now uses the unserved spec and the
leaf's repos under it. Mutation check: without it the dry run lists
`- r/README`, `- r/.git/…`.

**Tests.** `decide_unserved_tests.rs`: every reason × changed/unchanged,

## Probe: does rsync read `.gitignore` faithfully?

Fixture: root `.gitignore` = `/build`, `cache/`, `*.log`, `!keep.log`,
`.env*`; `sub/.gitignore` = `secret.txt`, `!*.keep`; plus `sub/build/o`, a
*file* `sub/cache`, `sub/deep/secret.txt`. `rsync -an --delete` with
`--filter=':- .gitignore'` and `--filter='dir-merge,- .gitignore'`:

| client | accepts both | nested | anchored `/build` | dir-only `cache/` | negation `!keep.log` |
|---|---|---|---|---|---|
| macOS openrsync (`/usr/bin/rsync`) | yes | yes | yes | yes | **no**: `keep.log` excluded |
| thistledown rsync 3.4.1 (protocol 32) | yes | yes | yes | yes | **no**: `keep.log` excluded |

Neither is a bug: in an rsync merge file a `!` line is not git's negation.
So the merge-rule route is out on both clients, and replicant materializes
the list.

Also probed, both clients identical: a line of an `--exclude-from` file
means exactly what the same text after `--exclude=` means (trailing space,
leading `#`/`;` after the `/`, `+ `/`- ` after the `/`, escaped `*`); an
`--exclude-from` list given to local openrsync reaches thistledown's rsync 3
over ssh in both directions (pull: the leaf's `.env.local` is not deleted,
ignored files are not sent; push: home's ignored files survive `--delete`,
rsync 3 notes "cannot delete non-empty directory"). Hide/protect rules
(`H`/`P`, `-s`/`-r`) were probed too and **diverge**: under `P /build/`
rsync 3 deletes `build/junk` while openrsync protects the subtree. Not used.

## The route chosen

`repos::ignored(repo)` lists what the repo's own `.gitignore` files ignore,
using the `ignore` crate's gitignore matcher (deepest file first, last line
wins, never descending an ignored directory, `core.ignorecase` read from
the repo's `.git/config`). Never the global gitignore, never
`.git/info/exclude`; nested repos and submodules not descended; symlinked
`.gitignore` not read (git ≥ 2.32 does not either).

**Not `git ls-files --ignored --directory`**, the route the brief
suggested: it collapses a directory by its *current contents*
(`sub/deep/` holding only `secret.txt` is listed as `sub/deep/`). Unioned
with the other side's list that hides the other side's new, unignored WIP
in `sub/deep/`. The list here names a directory only when a rule ignores
the directory itself.

**A tracked path is never ignored** (git's rule). Found by the timing run:
zed tracks `crates/project_panel/benches/linux_repo_snapshot.txt` under a
matching rule, and the first version would have stopped syncing it. A
tracked file drops out; a rule-ignored directory with tracked files is
listed by its untracked contents. `git ls-files -z --cached` runs only for
a repo where some rule matched.

Wiring: `SideUnit.ignored` (serde default: an older home sends none) is
each side's list minus what root excludes already drop. The snapshot adds
it to the unit's `Excludes` (hash filtering, case walk `all_names`); the
dry run excludes **the union of both sides' lists** as anchored literals,
so the source's are never sent and the target's are never `--delete`d. A
removal adds the leaf copy's list. Root `exclude`s still apply on top;
loose units are unaffected. Past 32 KiB of anchored rules they move to a
private mkstemp file under the config scratch dir (`rsync/spill.rs`).

`git status` now runs with `core.excludesFile=/dev/null`: a file hidden
only by the global gitignore (birchbook's: `**/.claude/settings.local.json`)
is synced, so the hash must see it as untracked work, the same on both
machines. **This changes repo hashes** for repos holding such files on
birchbook; harmless while v0.1 writes no baselines.

## Open

- **Newly force-added file vs. the other side's ignored copy.** The union

# Per-host certificates (v0.2 build list item 2; review Q1/F12)

Branch `bsneed/v0.2-certs`, one commit per step: `d6c972d` server/client

revoke, `ee4dd44` file splits. Each passes fmt, clippy and the full suite

## The flow

1. Home's first start mints its CA, `server.pem` (server use only, never
   leaves home) and `credentials.pem`, the **bootstrap** (client use
   only).
2. A new leaf saves the bootstrap as `home.pem` and runs `subscribe`. Home
   admits that over the bootstrap only for a host with no `[hosts.*]`
   entry, which records it as pending.
3. `approve` on home mints the host's client certificate, pins
   `[hosts.x] cert = "sha256:<DER fingerprint>"` in the same toml_edit
   write that enrolls it, and leaves the bundle in
   `state/issued/<host>.pem` (0600, directory 0700).
4. Until the leaf has `host.pem`, each of its commands first sends
   `HomeRequest::CollectCert` over the bootstrap. Home answers `Issued`
   (and deletes its copy before answering), `Pending`, or `Unknown`; for an
   enrolled host with nothing waiting it says to run `approve <host>`. The
   leaf keeps the bundle as `host.pem` (atomic, 0600), but only if the
   bootstrap's CA signed it.
5. From then on the leaf presents `host.pem`. After the handshake home
   hashes the peer certificate and looks the fingerprint up in fleet.toml.
   That is the host. A request naming another host is refused and
   journaled (`refused`, under the certificate's host). An unpinned
   certificate is refused and journaled before anything else happens.
   Heartbeat and Release also check that the caller holds the lease.
6. `approve <host>` on an enrolled host **reissues**: a new pin replaces
   the old one. The leaf's next command gets "unknown certificate",
   collects the new one over the bootstrap, and retries once (home refuses
   an unknown certificate before acting, so the retry repeats nothing).
   `host.pem` is replaced only when a new certificate arrives.
7. `replicant host revoke <host>` removes the pin and any certificate still
   waiting. Enrollment and subscriptions stay, and `approve <host>`
   re-admits the host.

**CollectCert vs a field on Subscribe's reply.** I made it a separate
request. Approval happens after `subscribe` has returned, so the
certificate does not exist when Subscribe replies. Some later request has
to carry it either way. A request of its own also gives the bootstrap
exactly two admitted operations, and it gives the leaf a way to learn
whether it is pending or unknown when it may ask nothing else. A pending
leaf's `status` is built from that answer.

**The client also checks home.** v0.1's one certificate carried both
server and client use, and every leaf held its key. After the upgrade it
is the bootstrap, and webpki alone would accept it from anyone posing as
home. So the leaf's verifier (`tls_verify.rs`) refuses a server
certificate that rustls' own client verifier would also accept. Home's
`server.pem` has server use only and passes. This needs no X.509 parser
and no new dependency.

**Wire version 2.** Mixed versions fail with the existing "run the same
replicant on both" / "restart the daemon" messages instead of half-working.

## Upgrading the deployed fleet (thistledown home, birchbook leaf)

There is no re-enrollment. Install the new binary on both machines, then:

1. **thistledown:** `systemctl --user restart replicant`. On start, home
   keeps `ca.key`, `ca.pem` and the v0.1 `credentials.pem` and mints
   `server.pem` from the same CA. The old shared bundle is now the
   **bootstrap**, good only for `subscribe`-while-unenrolled and
   collecting. birchbook is enrolled with no pin, so until step 3 its
   commands say: "birchbook is enrolled on thistledown but no certificate
   is waiting for it; run `replicant approve birchbook` on thistledown".
2. **birchbook:** `launchctl kickstart -k gui/$(id -u)/la.sovran.replicant`.
   The CLI and daemon must both be the new version.
3. **thistledown:** `replicant approve birchbook`. Nothing is pending, so
   it asks "birchbook is enrolled. Issue it a new certificate?"; answer
   `y`. That mints and pins the certificate, and it waits in
   `state/issued/birchbook.pem`.
4. **birchbook:** any command (`replicant status`) collects it into
   `~/.sovran/replicant/host.pem` and proceeds. Check with `replicant log`
   on thistledown for a `reissue` line and then a `collect` line.

**Optional: retire the old shared key.** birchbook still holds the v0.1
key, and it is still the bootstrap that `export-creds` prints. Leaves
refuse it as home, and home accepts it only for enrollment and collection.
To kill it entirely, after step 4 run `rm ~/.sovran/replicant/credentials.pem`
on thistledown and restart. Home mints a client-only bootstrap from the
same CA, and the old one becomes an unknown certificate. birchbook keeps
working on `host.pem`. Copy the new `export-creds` output to birchbook's
`home.pem` only if it will ever need to collect again (after a reissue).

## Known limits

- A pending entry's name is self-asserted by a bootstrap holder, and an
  issued certificate goes to the first bootstrap holder that collects it

  `subscribe` and the upgrade path, and PLAN accepts the bootstrap risk
  while every leaf is Brandon's.

- A revoked host's lease in flight is not released at once. Its heartbeats
  are refused, so it expires within one lease.
